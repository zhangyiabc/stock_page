# 小说写作流水线

当用户要求写一章新内容时，执行以下标准流程：

## 输入

用户需要提供：
- 章节号（如果是续写，自动取 progress.md 中的下一章）
- 本章简述或关键事件（可选，如果总大纲中已有则自动获取）

## 流程

### Step 1: 上下文收集（与 Step 1.5 并行）

使用 `sessions_spawn` 调度 `memory-keeper`：

```
task: "为第{N}章写作准备上下文。请返回：
1. 本章涉及的主要角色当前状态
2. 相关世界设定要点
3. 最近3-5章的摘要（从当前卷分片文件读取）
4. 当前活跃的伏笔列表（特别标出紧迫度高的）
5. 总大纲中本章的规划（如有）
6. 上一章的章末钩子（本章开头需要承接）
7. 当前文风指南要点（从 memory/style/style-guide.md 读取核心规则）

⚠ 返回值控制在 10000 字以内，精炼要点，不要复制原文大段落。"
```

### Step 1.5: 初步大纲框架（与 Step 1 并行）

使用 `sessions_spawn` 调度 `planner`：

```
task: "为第{N}章创建初步大纲框架。
章节简述：{brief}

先基于总大纲中你已知的信息，产出初步的：
1. 章节标题方向
2. 预期的场景结构（2-3个核心场景）
3. 爽点类型预判
4. 章末钩子方向

注意：下一步你会收到完整上下文，届时再细化。

⚠ 返回值控制在 1500 字以内，只输出框架要点。"
```

### Step 2: 章节规划（合并上下文 + 初步框架）

使用 `sessions_spawn` 调度 `planner`：

```
task: "基于初步框架，结合完整上下文，产出第{N}章最终详细大纲。
上下文：{Step1的输出}
初步框架：{Step1.5的输出}

请产出：
1. 章节结构（3-5个场景，每个场景含情绪基调）
2. 本章爽点设计：
   - 类型（打脸/升级/逆袭/揭秘/捡漏 等）
   - 如何制造压力（先压）
   - 如何引爆（再扬）
   - 读者能获得什么情绪（爽/燃/甜/虐/悬疑）
   - 如果本章无大爽点，说明"推进感"体现在哪里
3. 本章需要埋设/回收的伏笔
4. 章末钩子设计（必须明确，不允许'平着结束'）
5. 本章承接上一章钩子的方式
6. 信息控制：本章释放什么信息、读者会形成什么推测

⚠ 大纲控制在 3000 字以内，聚焦场景、爽点和钩子，不要写散文式描述。"
```

### Step 3: 正文写作

使用 `sessions_spawn` 调度 `writer`：

```
task: "按照以下大纲撰写第{N}章完整正文。
大纲：{Step2的输出}
上下文约束：{Step1的输出}
目标字数：3500字左右

特别要求：
- 严格执行大纲中的爽点设计：压得够狠、爆得够爽
- 章末必须有大纲设计的钩子，绝对不能平着结束
- 本章开头需要承接上一章的钩子
- 写完后执行自检：对照禁用词汇清单确认零命中、限用词未超标、无 AI 句式模式、有有效钩子"
```

### Step 4: 审校（含不合格自动重写）

使用 `sessions_spawn` 调度 `editor`：

```
task: "审校第{N}章。
正文：{Step3的输出}
上下文：{Step1的输出}
大纲设计：{Step2的输出}

按 review-checklist Skill 中的完整清单逐项检查。
报告第一行写 VERDICT: PASS 或 VERDICT: FAIL。
输出六维评分表和审校报告。
FAIL 时输出具体修改要求清单。
列出本章新埋设和已回收的伏笔。

⚠ 审校报告控制在 1500 字以内。PASS 时不要附带正文全文，只输出评分表、简评和伏笔记录。"
```

**审校结果处理：**

- **VERDICT: PASS** → 直接进入 Step 5 归档。报告中的 🟡/🟢 建议仅供参考，**不要调用 writer 改写**
- **VERDICT: FAIL** → 执行自动重写：
  1. 将审校修改要求传给 `writer`，要求逐条修复并重新提交完整正文
  2. 将修订版再传给 `editor` 复审
  3. 最多重试 1 次。仍然 FAIL 则**暂停流水线，通知人工介入**：
     - 用户选择"接受现状" → 以当前版本归档
     - 用户选择"提供修改意见" → writer 据此再修一版后归档
     - 用户选择"跳过" → 标记为待修订，跳过归档
- **异常情况**：如果报告中有 🔴 但 VERDICT 写了 PASS，按 FAIL 处理（有 🔴 就是 FAIL）

### Step 5: 归档

1. 将最终正文写入 `novel/vol{V}/chapter-{NNN}-{章名}.md`
2. 使用 `sessions_spawn` 调度 `memory-keeper`：

```
task: "第{N}章已完成。请执行以下更新：
1. 写入500字章节摘要到对应卷的分片文件 memory/plot/chapters/vol{V}-chapters.md
2. 更新 chapter-log.md 索引中的统计信息
3. 更新涉及角色的状态文件
4. 在 foreshadowing.md 的活跃伏笔表中登记新伏笔，同时写入 memory/plot/foreshadowing/vol{V}-planted.md
5. 标记已回收的伏笔，从活跃表移到 archived.md
6. 更新当前卷时间线分片
7. 更新 vocabulary.md 中的新术语（如有）
8. 记录本章的章末钩子内容（供下一章开头承接）
正文：{最终正文}
审校报告：{Step4中的伏笔记录部分}

⚠ 归档完成后只返回更新摘要，控制在 500 字以内。列出更新了哪些文件即可，不要回显文件内容。"
```

3. 更新 `memory/plot/progress.md`
4. 更新 `novel/metadata.md` 中的章节状态索引

## 批量写作

当用户要求写多章时（如"写第 8-12 章"），使用 `batch-write.prose` 流水线。

**核心原则：逐章串行，每章走完整流水线。**

- 每一章都按上面 Step 1 → Step 5 的完整流程执行
- 第 N 章必须完成归档后，才开始第 N+1 章的上下文收集
- **禁止**先为所有章节统一规划大纲、再统一写正文——这会导致后续章节无法感知前面章节的实际产出

原因：每一章的归档会更新角色状态、伏笔清单、章末钩子等。下一章的上下文查询依赖这些更新后的数据，否则会出现角色行为不连贯、伏笔丢失等严重问题。
